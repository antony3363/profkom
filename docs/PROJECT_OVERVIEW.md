# ПрофКом (ППОСиА ТПУ) — обзор проекта

Этот файл описывает проект с двух сторон: **что он делает** (функционально, для бизнеса) и **как это устроено** (технически, для разработчика). Описание опирается на текущий код в репозитории, а не на исходное ТЗ — там, где реализация расходится с ТЗ, это явно отмечено.

Смежные документы:
- [`API_FOR_FRONTEND.md`](./API_FOR_FRONTEND.md) — полный справочник HTTP-эндпоинтов по факту кода.
- [`ПрофКом_БД_диаграмма.drawio`](./ПрофКом_БД_диаграмма.drawio) — ER-диаграмма БД всех сервисов (генератор — `build_db_diagram.py`).
- [`ПрофКом_экономика_баллов.pptx`](./ПрофКом_экономика_баллов.pptx) — презентация по экономике баллов.

## 1. Функциональная часть

### 1.1 Что это

Мобильное приложение и веб-платформа для профсоюзной организации студентов ТПУ с геймификацией активности: студенты получают баллы ("профкоины") за посещение мероприятий и участие в жизни профкома, и тратят их в магазине на мерч.

**Бизнес-цель**: увеличить число вступающих в профсоюз первокурсников на 10% за первый семестр за счёт геймификации.

**Ключевые нефункциональные ограничения**:
- Авторизация — только через единый SSO ТПУ (OAuth2/OIDC, Authorization Code + PKCE). Без резервного входа по карте/паролю.
- Бюджет сервера — около 12 000 руб/мес (влияет на выбор инфраструктуры — см. раздел 3).
- Обязателен офлайн-режим на клиенте (кэширование) — вне зоны ответственности бэкенда, оговорка для фронтенда/мобильных клиентов.

### 1.2 Роли и что им доступно

| Роль | Смысл | Доступные действия |
|---|---|---|
| `STUDENT` | Авторизован через SSO, не состоит в профсоюзе | Просмотр каталога мероприятий/товаров, свой профиль |
| `UNION_MEMBER` | Член профсоюза (студент ПО) | + копит/тратит баллы, записывается на мероприятия, отмечается по QR |
| `PROFORG_SCHOOL` | Профорг школы | + подаёт заявки на мероприятия своей школы, награждает студентов из рабочего кошелька школы |
| `ADMIN` | Сотрудник профкома | Полное администрирование: роли пользователей, модерация мероприятий, каталог товаров, начисления без лимита |

**Важно**: это не иерархия на уровне кода — `ADMIN` не "включает" `PROFORG_SCHOOL`. Каждый защищённый эндпоинт сравнивает роль на точное совпадение (подробности и список проверок по каждому эндпоинту — в `API_FOR_FRONTEND.md`).

Профорги групп/направлений в текущей модели — почётные звания без функционала (не могут создавать мероприятия или распоряжаться баллами); реальные права есть только у профорга **школы**.

### 1.3 Экономика баллов

- Баланс баллов **не хранится** как число в профиле — единственный источник правды — леджер транзакций в `transactions_service`. Баланс — это агрегат (сумма по кошельку), а не поле.
- У каждого человека — **личный кошелёк** (`PERSONAL`), создаётся лениво при первом обращении (см. раздел 4.6).
- У каждой школы — **рабочий кошелёк** (`SCHOOL`), которым распоряжается её профорг; из него профорг награждает студентов за заслуги (не связанные с конкретным мероприятием).
- Кошелёк `ADMIN` — безлимитный (`unlimited=true`): списание с него не проверяет баланс. Это по сути "эмиссия" баллов в систему.
- Баллы начисляются за мероприятия через модерацию: профорг школы подаёт заявку → администратор принимает (фиксируя `pointsPerAttendee`) / откладывает / отклоняет.
- **Открытые вопросы по экономике** (не решены окончательно, см. `profkom_points_and_auth` в памяти ассистента, если нужна полная история вариантов): сгорание баллов студентов по курсам, иерархия лимитов на выдачу выше уровня школы.

### 1.4 Жизненный цикл мероприятия

```
DRAFT (SUBMITTED) → [ADMIN: accept] → PUBLISHED (APPROVED)
                   → [ADMIN: defer] → DEFERRED (можно вернуться к рассмотрению)
                   → [ADMIN: reject] → CANCELLED (REJECTED, финально)
```
- Подать заявку может `PROFORG_SCHOOL` (только для своей школы) или `ADMIN` (может указать любую школу либо `null` — служебное мероприятие, скрытое из публичного каталога).
- Каталог (`GET /events`) показывает только `status=PUBLISHED && schoolId != null`.
- Волонтёрские записи (`VolunteerRecord`) — отдельная сущность: человек регистрируется как волонтёр на конкретное мероприятие (для учёта помощи в организации, не только явки по QR).
- `Event.location` — свободный текст (nullable, без строгой структуры). Формат места проведения (онлайн/офлайн, обязательность, адрес как структура) — всё ещё открытый вопрос ТЗ, поле намеренно оставлено простым до решения заказчика.

## 2. Техническая часть

### 2.1 Стек

- **Backend**: Java 21, Spring Boot 4.1.0, Maven.
- **Межсервисное взаимодействие**: gRPC (синхронные вызовы с мгновенным ответом — например, начисление баллов при чек-ине) + Apache Kafka (асинхронные события — см. 2.4) + Spring Cloud Gateway/Eureka (внешний роутинг и discovery).
- **БД**: PostgreSQL 17 — отдельная база на каждый сервис.
- **Контейнеризация**: Docker Compose (локальная разработка; основа будущего прод-деплоя).
- **Документация API**: springdoc-openapi, агрегированный Swagger UI.

### 2.2 Состав сервисов (Maven-модули)

| Сервис | Порт HTTP | Порт gRPC | БД | Назначение |
|---|---|---|---|---|
| `eureka_server` | 8761 | — | — | Service Discovery (Netflix Eureka), сам не регистрируется |
| `gateway_service` | 8090 | — | — | API Gateway (Spring Cloud Gateway, WebFlux), единая точка входа, аутентификация |
| `auth_service` | 8081 | — | `auth_db` | SSO-заглушка, выпуск/валидация JWT, роли, refresh-токены |
| `events_service` | 8080 | 9080 | `event_db` | Мероприятия, модерация, волонтёрские записи |
| `check_in_service` | 8082 | — | `check_in_db` | Регистрация на мероприятие, чек-ин по QR, запуск начисления баллов |
| `shop_service` | 8083 | — | `shop_db` | Каталог товаров, категории, покупки |
| `transactions_service` | 8084 | 9084 | `transactions_db` | Кошельки, транзакции — единственный источник баланса баллов |
| `profile_service` | 8085 | 9085 | `profile_db` | Профиль, школы/направления/группы, назначение профоргов |

Имена Spring-приложений (`spring.application.name`) используются как Eureka service-id и совпадают с именами сервисов в `docker-compose.yml` (через дефис, не подчёркивание — важно для `lb://` URI в gateway).

### 2.3 Аутентификация и Gateway

Подробный разбор потока — см. историю обсуждения в репозитории/памяти ассистента; кратко:

1. Фронт логинится через `POST /api/v1/auth/login` (сейчас — заглушка SSO: `lichnostId` передаётся напрямую, без реального OIDC-обмена) → получает `{accessToken, refreshToken, expiresInSeconds}`.
2. Все последующие запросы — **только через gateway (8090)**, с `Authorization: Bearer <accessToken>`.
3. `AuthenticationGlobalFilter` в gateway на каждый запрос стирает клиентские `X-Lichnost-Id`/`X-User-Role`/`X-School-Id`, вызывает `GET auth-service/api/v1/auth/verify` для интроспекции токена, и подставляет свои — downstream-сервисы доверяют этим заголовкам без повторной проверки.
4. `accessToken` — JWT RS256, подписывается ключом, который генерируется **in-memory при каждом старте `auth_service`** — известное ограничение: рестарт сервиса инвалидирует все выданные access-токены (но не refresh-токены, они хранятся как хэш в БД).
5. Сервисы **всё ещё доступны напрямую** по своим портам в обход gateway (нет сетевой изоляции) — приемлемо для локальной разработки, требует закрытия для прод-деплоя.

### 2.4 Межсервисное взаимодействие

**gRPC** (синхронное, с мгновенным ответом пользователю):
- `check_in_service` → `events_service` (детали мероприятия) и → `transactions_service` (начисление баллов при чек-ине).
- `shop_service` → `transactions_service` (списание/возврат баллов при покупке).
- `events_service` → `profile_service` (поиск волонтёров по ФИО/группе).

Proto-контракты (`event.proto`, `person.proto`, `transactions.proto`) физически **продублированы** в каждом сервисе-потребителе (нет общего proto-модуля) — при изменении контракта нужно синхронизировать все копии вручную. Генерация — не через Maven-плагин (не работает из-за кириллицы в пути проекта), а через `scripts/generate-grpc.sh`.

**Kafka** (асинхронное, частично подключено — только 2 события):
- `UserRegistered` (`auth_service` → `profile_service`): при первом логине создаётся `AppUser`, публикуется событие; `profile_service` создаёт `UserProfile`, если пришли email/имя.
- `SchoolProforgChanged` (`profile_service` → `auth_service`): при смене `School.proforgId` снимается/назначается роль `PROFORG_SCHOOL`.
- Начисление/списание баллов (посещение мероприятия, покупка) — **намеренно** осталось на синхронном gRPC, не переведено на Kafka (сохраняет мгновенный UX-отклик).

### 2.5 Docker Compose (локальный стек)

`docker-compose.yml` в корне поднимает весь стек одной командой (`docker compose up -d --build`):
- 1× PostgreSQL 17 (порт хоста **5433**, чтобы не конфликтовать с нативной установкой на 5432) — `docker/postgres-init.sql` создаёт все 6 БД при первом старте.
- 1× Kafka 4.3.1 (KRaft, без Zookeeper) — dual-listener: `kafka:19092` для контейнеров, `localhost:9092` для хоста.
- 8 Java-сервисов, каждый со своим multi-stage `Dockerfile` (`maven:3.9-eclipse-temurin-21` → `eclipse-temurin:21-jre-alpine`).

Параметризация через переменные окружения (дефолт — `localhost`, поэтому нативный `mvn spring-boot:run` без Docker продолжает работать без переменных): `DB_HOST`, `EUREKA_URL`, `KAFKA_BOOTSTRAP_SERVERS`, `*_SERVICE_HOST` (для gRPC-клиентов), `AUTH_SERVICE_URL`, `SWAGGER_HOST` (для корректных ссылок в агрегированном Swagger UI при доступе с удалённого хоста, не `localhost`).

### 2.6 Swagger / документация API "на лету"

Единый Swagger UI собран в `auth_service` (временное решение до появления полноценного API Gateway документации): `http://<host>:8081/swagger-ui.html` — выпадающий список переключается между `/v3/api-docs` всех 6 сервисов. Каждый сервис дополнительно разрешает CORS для этого (`SwaggerCorsConfig`), т.к. запросы идут с другого порта/хоста.

### 2.7 Известные ограничения / технический долг

- SSO ТПУ не подключён — `auth_service.login` принимает `lichnostId` напрямую вместо обмена authorization code.
- RSA-ключ для JWT не персистентный (ограничение раздела 2.3).
- Сервисы доступны напрямую в обход gateway — нет сетевой изоляции.
- Нет outbox/retry для gRPC-вызовов начисления баллов — при сбое `transactions_service` баллы придётся начислять вручную (ошибка логируется, но не роняет сам чек-ин).
- Kafka подключена только для 2 событий из более широкого списка, предусмотренного исходной архитектурой (`EventPublished`, `BalanceChanged` и др. не публикуются).
- Docker Compose — только для локальной разработки: нет reverse proxy/TLS, секреты в открытом виде в `docker-compose.yml`, нет CI/CD.
- Часть эндпоинтов (см. `API_FOR_FRONTEND.md`, пометки ⚠) исторически были без проверки роли — по состоянию на дату этого файла основные дыры (категории/товары/медиа, обновление/удаление мероприятий, волонтёрские записи, просмотр чужих кошельков/профилей) закрыты; `purchase confirm/cancel/refund` и `transaction purchase-charge/refund` остаются открытыми намеренно — это сервис-к-сервис вызовы без отдельной service-to-service аутентификации (известное ограничение MVP).
